# OWP Agent 服务交付、验收与链上结算：建议方案

日期：2026-10-05。状态：研究建议，尚未实施。此文为内部中文材料。

## 1. 产品讲清楚：不是“给 Agent 发币”

客户购买一项固定范围的 Agent 服务，例如修复一个仓库中的缺陷。客户先把约定的测试代币放入合约托管；Agent 在授权范围内执行，提交产物与 OWP 证据；验证者复核，客户明确接受后，合约把资金释放给服务商。

工作名：**OpenWorkProof Settlement**。它可作为既有 OpenPay 商业方向的 Solana 试验切片，但没有因此把 OpenPay 写成已上线支付产品。

英文定位草稿：

> Fund an agent task, review verifiable delivery, and release escrow only with explicit customer acceptance.

第一用户假设是跨组织提供 Coding Agent 服务的团队和购买服务的小型软件团队。先回答“这一次修复交付，凭什么放款”，不建设 Agent 大市场或全球结算网络。

相对人工截图、聊天确认和一般托管付款，我们要验证的价值是：付款所依据的交付、授权、验证结论和接受决定可以独立复核。尚无证据支持降本比例、收入、商业采用或市场规模数字。

## 2. 为什么需要真正的链上应用

本次新增链负责三件事：预算锁定、授权条件下释放、可公开检查的资金状态。OWP 负责工作证据和验收语义；链不替代它。

```text
客户冻结工作单、收款方、金额及验收条件
  → 钱包存入 escrow
  → Agent 在隔离工作区完成任务
  → OWP 导出签名证据与验收包
  → Verifier 复核证据，重跑约定测试
  → 客户阅读结果，签署接受或拒绝
  → 有效接受 + 指定验证者共同授权
  → 合约原子地更新订单并转出测试代币
  → 查验最终确认、订单状态与代币余额，再显示 SETTLED
```

只在链上写一个摘要，没有资金锁定和释放，不是本方案的交付完成。只返回一个 RPC 交易签名，也不算结算成功。

## 3. 单链选择与首个可行性检查

| 选择 | 当前价值 | 代价或风险 | 建议 |
| --- | --- | --- | --- |
| Solana Devnet | 本届 Solana 生态奖；适合钱包、代币托管；加速器另要求 Solana 集成 | 本机 PATH 尚未发现 solana、anchor、rustc、cargo；工具链与部署需先验证 | 首选，先做一个 escrow 原型 |
| EVM 测试链（如 Base Sepolia） | 可采用 Solidity 的订单托管实现，OWP 仍可在链下工作 | 工具链也未验证；OWP Ed25519 签名不等于 EVM 钱包签名，桥的信任问题仍存在 | Solana 不可行时再评估，不并行开发第二条链 |
| 多链或纯上链存证 | 多生态展示或较低实现量 | 分散短赛期资源；纯存证不能证明付款闭环 | 本轮排除 |

推荐栈：**Anchor/Rust 合约 + TypeScript 钱包界面 + Python OWP 验证桥**。框架和版本在实际搭建时锁定，不能仅因这些名称存在就认为可编译。

第一检查：空白 escrow 程序能在本地编译、部署、收进和转出测试代币，并通过权限测试。若 10 月 6 日仍不能跑通，立即重新评估链与交付可行性；不通过删除必要权限检查来赶工。

Solana PDA 可用于确定性订单地址及由程序授权控制的 vault；Anchor 的 seeds/bump 约束必须验证。代币转账还需检查 mint、owner、authority、余额与金额精度，不能接收任意用户传入的账户。[Solana PDA](https://solana.com/docs/core/pda)、[Anchor PDA](https://www.anchor-lang.com/docs/basics/pda)、[代币转账](https://solana.com/docs/tokens/basics/transfer-tokens)

优先使用 Circle 公布的 Solana Devnet 测试 USDC mint：`4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU`。实施时再次核对网络、mint 和 decimals，并验证测试币获取。如果改用自建代币，明确叫 `DemoUSD`，不可冒称 USDC 或真实美元。两种演示代币均不代表实际收入。[Circle 地址表](https://developers.circle.com/stablecoins/usdc-contract-addresses)

## 4. 最小范围与权限

只做一个固定价、单次交付、无分账的代码修复订单。四个角色分开：Customer、Provider/Agent、Verifier、Escrow Program。Verifier 不是 Provider 可随意指定的同一身份；其地址及验证规则由双方在入金前冻结。

| 必做模块 | 成功标准 |
| --- | --- |
| 工作单与订单绑定 | 固定 revision、范围、测试、买卖双方、验证者、金额、mint、期限；得到可复核摘要 |
| 入金托管 | 买方钱包授权入金，vault 余额和订单状态一致；平台不接收用户钱包私钥 |
| 真实 Agent 执行 | Agent 读取任务、调用受控工具、产出补丁并运行测试；若使用固定 fixture，必须明说，不冒充自主执行 |
| OWP 证据与独立验证 | 验证签名与引用、重新执行约定检查；失败不能进入放款 |
| 客户验收 UI | 先展示产物、测试、范围与金额，再由客户主动接受/拒绝；后端不能替客户自动接受 |
| 双授权放款 | 合约检查固定客户及验证者均签署同一放款交易，并绑定订单和证据，才转账 |
| 结算对账 | finalized 确认、订单终态、正确 mint 的转账与余额变化互相对应 |
| 失败与退款路径 | 未交付超时退款、拒绝锁定、双方协商退款、重复交易与篡改被拒绝 |

不做：主网收款、平台持有客户私钥、代币发行融资、交易所、多链桥、自动仲裁、信用贷款、复杂里程碑、智能体市场、支付资质或法律正确性承诺。

## 5. 如何连接 OWP，而不误读已有代码

已有 `settlement.py` 是结算准备状态读取，不执行转账。已有外部 Acceptor 示例把签名进程分开，但会签收到的草稿，不能当作“客户阅读并同意”的产品界面。

保留 OWP 原有对象与协议，不直接修改 Core 的“非付款”边界。新应用增加独立 SettlementLink，将 OWP 对象、验收和链上订单互相绑定。

建议协议步骤：

1. 使用 OWP 原生 prepare/commit 接口生成验收草稿与复核信息。
2. 客户在浏览器阅读后签名。优先验证钱包 `signMessage` 能否签署 OWP 要求的 RFC8785、域分离字节，并通过 Core 原有验签；注册时冻结其公钥绑定。
3. 注意 OWP 的 `signer_key_id` 是原始 Ed25519 公钥的 SHA-256 标识，不是钱包地址字符串；算法相同不等于格式兼容。不得导出钱包私钥去调用 Python `sign_payload`，不得静默用后端私钥代签客户。
4. 若钱包不能签准确字节，停止该适配路线，再设计明确的独立 Acceptor 身份绑定。此兼容性目前未验证。
5. 验证桥检查完整验收包和当前有效状态，再针对特定链上订单、证据与接受摘要共同签署放款交易。
6. 客户钱包批准同一交易；合约在一笔交易内校验权限、更新终态及转账。浏览器隐藏按钮不能代替合约校验。

第一版本可使用客户和指定验证者对 `accept_and_release` 同一交易的双签，而非立即实现通用 OWP JSON 在链上解析。放款交易应绑定 network/program/job、订单版本、WorkOrder 摘要、证据包摘要、Acceptance 摘要、双方地址、mint、整数金额及有效期。合约检查冻结字段，不能允许调用者更换收款方或已提交的交付摘要。链上地址与 OWP 角色密钥的对应关系需由双方提前确认，不能在放款时临时换绑。

**信任边界：** 合约不能重新运行 Python 测试或判断交付质量。验证桥是被双方明确认可的 attester，必须公开其规则和控制方；这不是零知识证明或完全去信任化验证。不同密钥只证明角色分离，不证明操作人独立；单人演示若控制多个角色必须披露。

## 6. 状态机与争议

```text
FUNDED ──提交交付──> DELIVERED ──有效接受及双授权──> SETTLED
   │                     │
   │未交付且超时          │客户拒绝 / 撤回 / 争议
   ▼                     ▼
REFUNDED              DISPUTED ──双方同意退款──> REFUNDED
```

- 创建与入金宜原子完成；否则未入金草稿不能启动付费执行。
- 提交交付与未交付超时退款必须在合约内检查互斥状态；不得发生“已收到产物，还按未交付退款”。
- 客户拒绝不是自动判定服务商违约；进入争议，不自动给任何一方划走资金。
- 交付后客户失联：不自动认定接受、不自动放款；进入明确的争议处理流程。MVP 只支持双方同意的退款；僵局可能锁住资金，必须在 UI 告知。未引入可信仲裁前禁止真实资金使用。
- 已放款后的申诉只能追加记录，不能说撤回 OWP 验收能撤销链上资金。
- 链下状态和链上状态不是天然原子。OWP 撤回/暂停必须同步为链上阻断并获确认；只在链下改状态不能保证阻止已获签的待确认交易。
- 提案中使用订单版本和短时有效的双签交易降低竞态；“阻断已生效”以链上确认顺序为准。放款先确认时不能声称随后撤回已追回资金。

## 7. 必须验证的风险

| 风险 | 实现要求 / 测试 |
| --- | --- |
| 单方越权 | Provider、非指定客户、非指定 Verifier 不能放款；缺一个签名也失败 |
| 跨订单替换 | 更换任务、bundle、acceptance、收款地址、mint 或金额失败 |
| 重放与双花 | 一份授权不能用于另一订单/网络/程序；同一订单不能重复放款 |
| 时间与状态竞态 | 超时、提交、拒绝、退款与放款之间有确定的互斥规则 |
| RPC 中断 | 交易状态未知时先查链再重试；签名产生不等于成功；不重复入金 |
| 证据失效 | REFUTED、REJECTED、撤回及缺失证据都不能获得桥的放款签名 |
| 验证桥作恶 | 客户仍须批准；公开其信任假设，不宣传自动保证质量 |
| 私钥与密钥泄露 | 客户私钥不进入 API/日志/仓库；验证者密钥不提供给 Agent |
| 隐私与可用性 | 链上不放私有代码或个人信息；摘要不能保证文件可取回，演示须能下载完整包 |
| 金额精度 | 链上使用整数原子单位；不可用浮点金额；检查 mint decimals |
| 撤回不同步 | 明示链下撤回与链上阻断的差异；测试待确认交易竞态 |

Demo vault 由程序控制，但若升级权限仍由开发者掌握，就不能宣传“平台绝对无法触碰资金”。部署记录必须标注 upgrade authority；真实资金上线前需要另行审查升级、暂停、仲裁与用户风险。

## 8. 首个演示与商业验证

固定案例：修复一个小型公开或自有测试仓库的缺陷。冻结源 revision 和验收测试；先展示失败，再由 Agent 修复；独立验证环境重跑测试；客户看到补丁与结果，明确接受；测试代币从 vault 转至 Provider。

必须同时展示一条负面案例：篡改证据或测试失败时，客户不能通过正常流程放款、合约也拒绝缺少有效授权的转账。仅播放成功路径不足以证明权限边界。

需求验证先访谈 2–3 位实际提供或购买 Coding Agent 服务的人，记录当前如何约定成果、判断完成和付款。访谈为建议，尚未联系任何人；社区交流、目录收录和开源 PR 不自动算客户需求或付费订单。

收费先验证“固定范围交付工具/验证服务”的单次或订阅模式；链上手续费由网络产生，不能直接当作本产品收入。暂不公布抽成、客户数或收入预测。
